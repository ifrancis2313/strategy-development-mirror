# Confirmation: a one-shot, frozen-parameter check against the untouched post-2019 reserve, partitioned to survive contact with reality

## Status

Accepted as framework. Cannot be exercised until a licensed post-2019 data feed exists (Polygon.io, per the standing data-licensing policy) — same "framework fixed now, mechanism follows once the dependency lands" treatment ADR 0004 gave the Shadow graduation gate ahead of `shadow/ledger.py` landing.

## Context

ADR 0006 established that everything tested against `all.parquet` (OptionMetrics SPX chain, 1996-2019) is exploratory, not confirmatory, and that the only real fix is genuinely new data — the 2019-present window, once a licensed feed exists to source it. What ADR 0006 didn't pin down is the mechanics: how that reserve gets consumed without becoming a second `all.parquet` through the exact same abuse pattern (repeated testing, revise-on-failure, researcher priors drifting toward whatever the sample rewards).

One naming correction before the mechanism: what's being proposed is **not** `testing/validation/walk_forward_validation.py`'s walk-forward (rolling refit across folds, selecting among candidates each fold). By the time a candidate reaches this gate, its parameters are already frozen (Graduation is a frozen-snapshot copy — see `CONTEXT.md`). There is nothing left to tune or select on the reserve data. Calling this "a walk-forward check" invites conflating it with the in-Testing tuning machinery, which would reintroduce a selection step exactly where the whole point is to have none. This is a single, frozen-parameter backtest run against one allocated slice — closer in shape to Shadow's own live-vs-predicted divergence check (ADR 0004) than to anything in `testing/validation/`.

## Decision

**New term, added to `CONTEXT.md`'s glossary: Confirmation.** The one-shot, no-tuning evaluation of an already-frozen strategy snapshot against a slice of data no Testing-wing experiment has ever touched. Required, alongside `testing/graduation/bar.py`'s existing statistical criteria, before Graduation (Testing → Shadow) may proceed. Distinct from Graduation itself (the act of copying frozen code across wings) and distinct from Shadow's own graduation gate (ADR 0004, which checks live-vs-backtest divergence *after* Shadow has accumulated real trades) — Confirmation is the missing middle piece: a genuinely out-of-sample check that happens *before* committing a candidate to Shadow's slow real-time clock.

**Where it sits:** `all.parquet` exploration + `bar.py` criteria (exploratory) → **Confirmation** (the first confirmatory check) → Graduation → Shadow → Shadow's own gate (the second, stronger confirmatory check, on live data) → Pipeline.

**Mechanics:**

1. **Frozen parameters, single run, no selection.** Confirmation runs the exact already-graduation-candidate snapshot once against its allocated slice via the ordinary backtest engine (`testing/engine/backtest_runner.py`), not `run_walk_forward_validation`. There is no train window on this data — nothing gets tuned here.
2. **Reuse the existing divergence-check method, don't invent a fourth statistical tool.** Pass/fail compares the Confirmation slice's observed Sharpe against the distribution `all.parquet`'s backtest + Monte Carlo predicted — the same null-distribution comparison `testing/monte_carlo/mcpt.py` already does, and the same approach ADR 0004 already prescribes reusing for Shadow's divergence check. Confirmation and Shadow's gate end up sharing one method, applied to two different data sources (a historical fresh slice vs. a live ledger) — consistent with this repo's existing "reuse rigor machinery, don't reinvent per stage" principle.
3. **Slices are sized to the candidate, not to a fixed calendar chunk.** A strategy trading ~20 times/year needs a different span than one trading weekly to hit a statistically meaningful trade count — the same principle ADR 0004 already applies to Shadow's track-record length. Concretely: request enough contiguous calendar time, starting from the oldest unconsumed date in the reserve, to reach roughly the candidate's own observed `all.parquet` trade frequency × a target minimum trade count. **The target trade count itself is deliberately left open, not guessed** (default placeholder ~30-50, ADR 0003/0004-style `not_yet_defined` until this gate is actually exercised once for real and there's a real number to calibrate against).
4. **Consumption is strictly chronological, first-come-first-served, and permanent.** Slices are assigned oldest-unconsumed-first from one shared reserve tracker. Once a slice is assigned to a candidate, it is retired forever — regardless of pass or fail, regardless of strategy family — and never reassigned to anyone, including a revised version of the same candidate. This is the load-bearing rule from ADR 0006, operationalized: a Confirmation **failure retires the candidate outright**. The next slice goes only to a genuinely independently-conceived new candidate, never a tweak-and-retry of the failed one. Allowing a retry — even on a different slice — reintroduces the exact researcher-degrees-of-freedom problem ADR 0006 diagnosed, just relocated onto a scarcer resource.
5. **The reserve is self-replenishing, unlike `all.parquet`.** Every calendar day that passes without being consumed adds one more untouched day to the reserve — this is a fundamentally different resource than the frozen 1996-2019 file, which will never grow. As long as the rate candidates reach this gate stays below the rate real time accrues, exhaustion isn't a structural risk the way it was for the historical file. Still, the ledger below exists for transparency, not because the reserve is expected to run dry.
6. **Ledger (spec only — not yet built, no data exists to log against yet).** Two distinct pieces, not one: (a) the *consumption boundary itself* lives in Supabase as a column/flag on `chain_snapshots` (see point 7) — the actual, query-enforced ceiling, not just a paper record; (b) a per-candidate audit record, mirroring `testing/graduation/manifest.py`'s existing frozen-snapshot pattern, written alongside that candidate's graduation manifest: candidate name, its graduation-manifest reference, the assigned date range, date assigned, pass/fail, observed Sharpe/MCPT result. (b) is human-readable history; (a) is what actually stops a slice from being reread. No heavier system than these two needed.
7. **The reserve lives in Supabase, not a local file (decided 2026-07-11) — and this is a materially better home than a second `all.parquet` would have been.** Polygon data gets read into the same shared `chain_snapshots` table Ingestion already owns (`ingestion/supabase_client.py`), via a new `ingestion/sources/polygon_source.py` alongside the existing `yfinance_source.py` — not a new local parquet file. `ChainSnapshot`/`ContractRow` (`ingestion/schema.py`) are already source-agnostic (a `source` field on both, ported verbatim from OFP), so this needs zero schema redesign. More importantly, `chain_snapshots` already carries a `usable_for_trading` boolean, hard-gated and defaulting `False` for anything not confirmed-licensed (yfinance never qualifies, per the standing data-licensing policy) — the exact same shape of "don't let this be used until explicitly cleared" gate Confirmation's consumption tracking needs. The operational risk flagged in the original draft of this point — nothing stopping an ordinary script from accidentally reading unconsumed dates once the data exists locally — is meaningfully reduced by this: a query-level filter against Supabase (e.g. a `confirmation_consumed_at IS NULL` condition, or reusing/extending the existing gate column) is a much smaller, more central surface to guard than "don't let any script open the wrong local file." **Still spec only, not built** — no code should be written for this until Polygon is actually subscribed (see the boundary noted in `feedback_build_through_missing_credentials`: there's no real interface to build/mock yet, only the absence of the data itself). **Separately not yet decided, flagged so it isn't conflated with this decision:** whether Polygon also replaces yfinance as Ingestion's source for *ongoing* daily snapshots (a different question from backfilling the historical Confirmation reserve, which is a one-time bulk pull, not the existing daily-cadence `run_yfinance_ingest.py` shape) — Zi's call whenever Polygon access exists, not assumed here either way.

**Not yet decided:** the exact default minimum trade-count target (left as `not_yet_defined`, per ADR 0003/0004's own convention, until this gate is exercised for the first time); whether Confirmation happens strictly before Shadow or could run in parallel with Shadow's early trades (current default: strictly before, since it's cheaper and faster than waiting on Shadow's slow clock, and a failure here should retire a candidate before it ever spends calendar time in Shadow).

## Consequences

- A candidate now needs to clear two structurally different checks before Graduation: `bar.py`'s exploratory statistical criteria (MCPT/PBO/named-source/sensitivity, on `all.parquet`) and Confirmation (one-shot, on the post-2019 reserve). Neither substitutes for the other — passing one without the other is not enough.
- A well-designed strategy that draws an unlucky short window has no recourse under this rule but to be redesigned from scratch as a new, independently-conceived candidate and wait for the next slice. This is a real cost, accepted deliberately: the alternative (permitting a retry) is exactly the abuse this protocol exists to prevent.
- This reserve is genuinely scarce only if consumption outpaces real time — worth revisiting the partitioning defaults if this repo ever reaches a stage where many candidates are queued for Confirmation simultaneously (not the case today; nothing has graduated yet).
- The technical guard against accidentally querying unconsumed dates is not yet built and carries real risk of being skipped under time pressure once real data exists — flag this explicitly when the Polygon.io build actually starts, rather than assuming discipline alone will hold.
